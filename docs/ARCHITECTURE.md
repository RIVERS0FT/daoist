# 架构与扩展说明

## 2026-09-22：RIVERSOFT 自动发布边界

`.github/workflows/deploy-riversoft.yml` 是静态游戏的独立发布入口：`main` 推送或手动运行会先在 Node.js 22 上执行源码检查、1011 项规则/HTTP 测试、Chromium 交互回归、单文件构建和 RIVERSOFT CLI 文件检查，再把已验证的 `dist/` 作为一天期工作流产物交给独立发布任务，以 `daoist` slug 发布公开版本。`production` 环境中的 `RIVERSOFT_TOKEN` 只注入发布任务；发布网络失败时可只重跑失败任务，不重复运行浏览器回归。`tools/riversoft.mjs` 是审核后的无依赖 CLI 副本，仓库、产物和日志不得出现令牌。CLI 不执行远端构建，也不发布源目录，只上传带根 `index.html` 的 `dist/`。

发布完成后工作流优先接受 API 返回的 `https://<account-subdomain>.riversoft.top/daoist/` 地址，并下载同一地址的 `index.html` 与本次 `dist/index.html` 做 SHA-256 比对。若该地址的 DNS/TLS 尚未完成，工作流不绕过证书，而是发出警告并改用 HTTPS 主站兼容地址 `/p/daoist` 及带 deployment ID 的内容接口做同样的哈希验收；这表示内容已发布，但不表示用户子域名已经具备可用证书。GitHub Pages、仓库 CI 和 RIVERSOFT 发布是互相独立的状态，不能用其中一个替代另一个。

RIVERSOFT 的网页运行在受限静态沙箱中，禁止持久化存储、外部网络和服务端代码。因此该地址用于经典单文件游戏的托管体验；AI 模式仍需要本机 `npm start` 代理，线上沙箱也不能被描述为跨刷新云存档或多人后端。

## 1.18.0：十二章人物化扩写（2026-09-23）

本版继续扩充既有十二章，不增加第十三章，也不把主线改成新的分支树。目标是让“章节”不只承担境界和配送门槛，而能持续呈现主角、外卖系统器灵与已结识人物如何理解同一件事。应用版本升为1.18.0；存档结构仍为v21，存储键仍为`night-courier:saves:v21`，没有新增持久化字段、主线标记、奖励或经济渠道。

### 三层章节内容

第一层是`G.STORY_STAGES`与高境界章节的章节描述。十二章都补充了当前矛盾、人物立场与阶段性问题：第一章从“完成十单”落到普通骑手为什么仍愿意把饭送热；第二章强调得到力量后生活并未被跳过；第三章学习区分线索、历史与想象；第四章把修行圈写成有交班、疲惫和边界的具体人群；第五章拒绝把人压平成“阵点”；第六、七章分别处理系统的回避与真相；第八至十二章继续推进同意、旧连接、共同承担、经验传承与渡劫后的自主选择。

第二层是原有固定剧情正文。保留全部既有事件ID、章节门槛、三个选项、效果、成本、耗时和完成标记，只扩写正文与人物反应：首单、第一章第十单系统解锁、`story-street-vein`至`story-system-truth`五场前期主线，以及化神至渡劫十场高境界主线。器灵因此形成连续的人物弧线：从只会计算“有效连接”，到无法解释人的差异；从害怕连接减少、拒绝回答，到承认旧阵失败；再学习说明、等待同意、接受沉默与结束、分散责任、允许善意不被计数，最终不再给玩家唯一答案。它仍是固定主线角色，不交给AI改写。

第三层是只读的章节人物侧写`G.CHAPTER_CHARACTER_BEATS`。十二章各有一个章节问题和3–4条人物视角，共覆盖全部21位具名NPC；`G.chapterCharacterNotes(s, stageId)`只返回`bonds[id].met===true`的人物，并补姓名与职业用于显示。查询不推进时间、不抽随机数、不发奖励、不结识人物、不改变关系，也不会把章节侧写写进存档或AI上下文。外卖系统“委托”页在任务列表前展示当前章描述、章节问题和已结识人物的旁注；没有匹配人物时只显示提示，不列出隐藏姓名。

章节侧写用于强化人物既有性格而不是创造新能力。例如陈默以“人也得歇”理解第一章，程砚秋以“宁留缺口、不猜字”回应第三／九章，林晚从包办转向轮值回应第五／十章，江临用可解释和可维护的系统观回应第六／十一章。人物仍保留各自个人故事、职业边界、常约地点和关系路线；侧写不是个人剧情结算，不能推进`bonds.stage`。

### 剧透与人物边界

未结识人物绝不出现在章节侧写中。章节卡只展示当前章，不用全人物目录提前曝光后续角色。周野只在第一章侧写出现一次，内容严格停留在普通骑手、同行互助与跑单经验，不出现修仙、灵力、黑签、蚀灯会、组织、背叛或仇人等后期信息；其第六段／第七段实际结算后的分阶段身份规则继续由1.17.0约束。

委托奖励文字也同步修订，避免旁路剧透主线。旧q3在炼气阶段直接宣布系统是护城阵，早于第六、七章的“追问→真相”节奏；本版改为只描述看见异常、继续求证。q1–q8只补叙事与人物主题，不修改ID、完成单数、境界要求或奖励。已经结算的历史回执和日志仍按原保存内容保留；静态配置更新只影响之后展示／未结算的可信模板。

### 规则、兼容与验证

第一章仍要求先完成九单，再把第十份热饭送至非常驻随机地点并完成固定选择后解锁外卖系统；解锁单本身仍没有外卖币，第二章仍须领取q1才开放修行。第三至第十二章的境界、配送数、前章完成关系不变。宗门、周野十段线、21位NPC个人故事、女性感情线、丹方、炼药、拍卖、道路、电动车、房租优先、暂停／停止与结局均不改。

应用版本1.18.0只表示内容与只读界面扩充，存档继续v21；因此旧档无需迁移或重开，资产、关系、主线标记、进行中行动、票据、历史结果与日志都不补算、不重置。新增专项测试覆盖十二章／21人侧写完整性、未结识过滤、查询纯度、周野前期防剧透、固定主线ID与三选项稳定性以及未知章节边界。完整验证记录见`docs/TEST_REPORT_1.18.0.md`。

## 模块关系

程序使用原生 JavaScript IIFE，各模块向 `globalThis.NightCourier` 注册数据和函数。浏览器加载顺序：`data → engine → clock → storage → progression → map → app`。服务端只导入 data/engine 做共享内容校验，不访问 DOM 或浏览器存储。

```text
玩家指令 → app → G.perform(旧状态, 行动, 参数)
                     ├─ 校验失败：原状态不变
                     └─ 即时事务，或建立 activity（不跳时）

单一 requestAnimationFrame → GameClock（暂停集合 / 倍率）
                                ↓ 经过的游戏分钟
                           G.advance(旧状态, dt)
                                ↓
       路段坐标 / 资源积分 / 跨日房租 / 行动完成 / 待选事件
                                ↓
       地图局部渲染、状态栏节流更新、周期与关键节点自动保存

待选事件 → 本机 /api/story → 白名单校验 → 校验事件/存档/请求序号
                                          ↓
                                只替换未结算事件内容
```

## 选择后结果与配送扩充（1.9.0）

剧情交互现在分为「待选 → 执行（有耗时才出现）→ 已结算结果 → 确认继续」。结果页是当前事件的一次性回执，不是第二份历史列表；行为与事件历史仍只保存在右下角日志。界面展示事件标题、所选行动、该选项的结果文本、实际数值变化，以及单独列出的配送结算。探索、修炼、人物章节和主线选择共用这一流程；拍卖出价继续使用专用轮次及图录结果，不把竞价当作普通剧情选择。

`finishChoice` 是 `eventResult` 的唯一创建点。零时长选择在同一事务中结算，耗时选择由 `G.advance` 到达真正完成节点后生成回执，不能提前发奖或解锁地点。选择的资源变化与 `settleDelivery` 的到账变化分别从规范化后的真实状态差计算；扣费/物品成本由已提交选项重建，不跨整个耗时区间做差，因此同刻房租或途中即时兑换不冒充选择成本。数值上限以实际变化为准。回执没有可执行效果、重放选项或奖励票据。

v14 新增独立的 `eventResult`，字段为 `id/title/choice/text/source/at/duration/changes/delivery`；`changes` 为已发生的 `{key,delta}`，只允许角色可展示属性、白名单消耗品和已定义人物好感/信任。`delivery` 只包含订单标题、已解锁目标与实际变化。`cleanEventResult` 限制文本、时间、数量、键和值，拒绝损坏记录或与未交付订单/其他活动冲突，丢弃注入的 effects/reward。唯一允许同时存在的活动是尚未推进的救助；确认按钮不能被通用“活动进行中”规则禁用。

`G.advance` 以及时钟事件暂停都在有结果时冻结。`ackResult` 必须匹配结果ID，只清除回执并增加 revision，不扣费、不发奖、不增加 turn、不抽随机数、不刷新订单、不执行完成钩子；重复或过期确认及其他游戏指令原子拒绝。读档默认手动暂停，阅读时消耗的墙钟时间不会补算。结果优先于地图、快捷面板和下一段剧情，Esc/遮罩不能跳过确认。

完成选择时，原有 `markComplete` 仍可排入一个主线 `pending`；结果与下一段主线分开保存，先展示结果，确认后才显示主线，防止第三单等里程碑覆盖刚选的结局。AI不会在结果阅读期间启动新请求，迟到回复不能覆盖已结算内容。故事标记和丹方奖励仍按真实完成条件判断，不把“已注入”当成已完成。

v1–v13 迁移新增空结果，不从旧日志补造回执或重发奖励。旧待选事件、旧耗时选项继续按原进度执行，完成后才进入新流程。存储键升为 `night-courier:saves:v14`，缺少新键才依次迁移 v13 至 v3，原文保留，多档相互独立。

配送内置事件新增39个，总计60个/180个选择。新增日常配送、邻里互助、夜班生活、骑手协作和都市修仙奇遇；每项有不同的结果文本与规则效果，每个事件至少有一个无支付障碍选择。既有21个事件、人物、主线和订单模板保留；`G.EVENTS` 总计79项（配送60、探索8、修炼6、主线5），人物四章另计。保持原有触发概率与近期去重，不增加按帧随机、不改地图或订单经济。

## 规则引擎与事务边界

`G.perform(original, action, payload)` 先复制状态并校验。失败返回原对象和中文原因；成功只提交即时事务或开始持续行动。世界内时间只由 `G.advance(original, gameMinutes)` 推进，界面不直接写位置、余额、时间或奖励。两个接口均不修改传入状态。

`progression.js` 包裹 `G.perform` 检查商城解锁；通过 `G.afterWorldAction` 在真正完成世界行动后注入主线，不在点击出发时注入。`gameOver` 后不接受指令；待选剧情和结局会冻结推进。

同时只能有一个 `activity`。`stop` 保留当前位置、实际消耗和已经获得的渐进收益；已接单继续计时，使用 `resumeDelivery` 继续，或 `cancelDelivery` 明确取消且无报酬。停止不是暂停。执行行动期间只允许可中断行为停止以及零耗时 `buy/sign/claim`；已提交的拍卖轮次与耗时事件选择不可停止；换交通方式、服药和另一个耗时行动须先停下。

## 外卖发现地点（1.7.0）

地点所有权保存在v12 `unlockedPlaces`，新档由 `G.STARTING_PLACES` 独立复制 `home`、`garage`。这是用户指定的初始例外，其他地点仍通过成功交付解锁。`G.placeUnlocked`、`G.visibleServicePlaces`、`G.visibleResidences` 为只读查询；不从位置、已接订单、NPC关系或渲染行为猜测发现。`settleDelivery` 在原配送奖励实际结算后调用 `G.unlockDeliveryPlace`，首次才追加白名单地点和一条「地点」日志，不额外发奖、不推进时间。待选配送和耗时选择仍未结算，中断、取消、救助、房租终局均不能发现。

`G.locationBlock` 在核心 `perform` 中与已有 `featureBlock` 独立校验：自由赶路、搬家、拜访、维修/升级、治疗、探索、用餐、药摊购买及拍卖图录/出价要求地点已发现。当前已接订单目的地的继续赶路允许通过，以保留停止、改道与续送；尚未接取的地图订单不授予自由赶路权限。正常 `deliver` / `resumeDelivery` 仍可进入未知地点。原地休息、充电、步行、当前住处睡眠、用药与受伤救助不受阻，AI不接收地点授权字段。

`refreshOrders` 保留前两个近单名额。从第三个名额起，若现有待接/在途订单中没有未知常驻地点，优先补最近的未知常驻地点；其余名额继续原随机规则。保底依赖真实订单空缺，不从开面板、地图重绘或即时兑换刷新，允许所有110个地点成为订单目标，不修改路网、旧坐标、价格、资源消耗或订单总数。

地图常驻底集改为 `visibleServicePlaces`，叠加待接与已接订单；普通配送地址即使已发现也不加入常驻底集。未知订单显示「首次送达后解锁地点」，详情仅提供订单和接单入口，不显示当地描述或服务；发现状态改变时更新对应标记。`routeButton`、羁绊、住宅、炼药与拍卖面板共享地点校验，不能只隐藏地图而保留快捷绕行。所有权不等于玩法条件达成，发现长乐集不赠送药鼎或提前解锁炼药/拍卖。

`sanitizeSave` 对v1–v11保留原本已开放的固定地点，以及旧非配送行程/非待交付当前位置；不将普通地址未结算配送（含耗时选项）误认为已经成功。v12要求有效白名单数组、起始小屋和当前住宅，去重但不静默清空损坏记录；1.7.1 在校验后补齐修车铺初始权限，不改变资产、时间、订单或其他地点，也不发送发现奖励；恢复活动后交叉检查地点权限，拍卖记录还要求长乐集权限。旧存储键迁移保留原文，多存档独立，读档默认暂停。客户端完整性校验不是服务端防作弊。

## 玩法渐进开放（1.5.0）

`data.js` 的 `FEATURE_UNLOCKS` 是功能 ID、门槛、前置、提示与解锁日志的唯一配置；`FEATURE_PANELS` 映射系统、修行、炼药、羁绊与拍卖五个受限面板。新档仅显示行囊、座驾、歇息、帮助；地图接单、基础生存、时间控制、日志、角色资料和存档不受门槛限制。初始物品可继续通过行囊使用。

现行功能顺序为：九单完成后，第十单固定剧情实际结算 → 系统；领取 q1 → 修行/吐纳；完整修炼一次 → 进阶功课/突破/探索；已开放修行且送达至少三单、street-vein 主线完成 → 炼药；五单 → 升级；已开放炼药且十单 → 拍卖；二十单 → 系统归途。羁绊独立在遇见第一位人物时开放。前置配置只用于必要依赖，不强迫玩家完成所有其他玩法；系统解锁后才开放依赖它的成长玩法，不要求先走情感线；炼药的三单数值门槛保留，但仍必须完成绑定、q1领奖及路线主线。

`G.featureUnlocked` / `G.panelUnlocked` / `G.nextFeatureUnlock` 是纯查询，不从渲染写入状态。查询既检查已持久化所有权，也计算当前已完成条件。`G.featureForAction` / `G.featureBlock` 在核心 `G.perform` 中统一拦截受限指令，失败返回原对象，不扣钱、不推进时间/随机源；商城的额外境界限制仍由 progression 包装层检查。不能仅隐藏 UI 却保留可提前执行的业务指令；客户端校验仍不等同防作弊。

`G.syncFeatureUnlocks` 在成功事务末尾和世界行动实际完成后调用，在 `afterWorldAction` 注入主线之后判断，防止把主线待选状态当作完成。`formulaStoryComplete` 同时排除待选主线和进行中的耗时选择。首次修炼只有真正完成才增长 `stats.trained`；中断不解锁。与房租同刻的失败仍优先，终局不发新解锁。已开放 ID 永久保存，历史只记一条右下角日志；1.9.2 起另保存一次性功能回执供弹窗确认，不赠物、不改时间、不依赖 AI 回包。

界面所有导航、顶部系统货币入口、地点服务卡和面板快捷入口使用同一查询；`openPanel` 在改变暂停/对话框前拒绝受限面板，系统子页也单独校验。炼药从修行面板拆成独立导航，未到开放条件不显示。修行初期只出现吐纳；升级和归途内容按条件出现。系统商品按境界过滤而非罗列所有锁定项目，药鼎/药材也只呈现当前境界开放项（已拥有药鼎保留）。`G.visibleQuests` 返回已领篇章与第一篇未领委托，领取后续委托在规则层同样拒绝跳过；丹方仍遵守 1.4.2 的所有权与三渠道规则。

导航数量增加时在手机上内部横向滚动，按钮最小宽度 44px，不撑宽整页。顶部只切换货币/灵力节点的 hidden 属性，不替换时间倍率选择框。切换存档清空上一次系统子页和破境丹勾选；帮助集中列出各功能状态与条件，地图只保留下一步短提示。

## 万宝拍卖场（1.6.0）

`AUCTION` 保存地点 market、开放 18:00–24:00、每日三件拍品、每轮五分钟、起拍/加价比例和预算步数上限；`AUCTION_BIDDERS` 是三位匿名竞拍者，不复用 NPC 羁绊。功能配置要求 `alchemy` 前置与十单实际交付，导航、市场快捷卡和核心指令共用门槛。没有新增或移动地图节点，异地入口只能查看已缓存图录并规划真实路程，到场才能生成当日图录或出价。

`auctionCatalog` 是零耗时事务，首次到场查看当日图录时才调用世界 RNG：药材包（3–5）、成品丹药（1–2），以及未拥有、境界允许的药鼎（1）；未购过药鼎或当前境界无缺失鼎时，第三件换另一包药材。品阶境界使用与炼药素材共用的 `ALCHEMY_REALM_BY_TIER`。不产生丹方、独占功法或人物解锁。当天图录不随面板、帧、读档或境界提升再抽，新一天首次查看替换旧图录，但保留累计成交数量与支出。

`auctionLotInfo` 为价格与展示唯一来源：药材/鼎沿用原现金价格；丹药单价为 60+25×阶数，破境类再加60，乘数量得参考价。起拍为参考价×0.65向上取整至5元；加价步长为参考价×0.08向上取整至5元且至少5元。每位对手的隐藏预算为起拍价加 0–8 个步长，创建图录时一次确定。对手行为与画面帧率、AI、刷新次数无关，不承诺竞得价总比固定商店便宜。

`auctionBid` 或拍卖待选事件中的继续竞价先原子校验地点、开放时间、剩余完整轮次、资格、所有权、库存容量、报价和现金，再全额冻结资金并建立 `activity.kind='auction'`。一口/三口分别加一个/三个步长（首拍以起拍价计第一口）。一轮5分钟只由 `G.advance` 推进，提交后不可中断；`startAuctionBid` 不发奖励、不跳时间。其他拍品与当地行动不能并发；保留系统 buy/sign/claim 即时事务，但限制同物品兑换以预留即将成交的库存空间，现金上限也减去冻结款以保留完整退款空间。

`finishAuctionBid` 在实际完成节点检查预先封存的预算：有对手能再加一步时，轮流选符合预算的对手抬价、退还全额冻结款，并生成经典三选项 `pending.kind='auction'`（一口/三口/免费退出）；无对手则落槌，将冻结款结转为支出，增加对应物品或药鼎收藏并累计 wins/spent，不再次扣现金、不自动换鼎。最后一轮超价且无时间再开轮时退款并标记 lost，不产生过期事件。待选时沿用全局事件暂停，选择后才开始新一轮；成交/退出自动返回拍卖面板，不增加独立计时器。

世界跨日先收租，冻结款不算可用现金；午夜破产会中止同刻竞价结束，不发退款或拍品。只在成功完成节点生成对应日志，拍卖面板不重复列历史日志。时钟文本容忍 1e-8 分钟的积分浮点尾差，避免18:05的完成节点显示18:04，但不改变状态时间或任何结算门槛。

`auction={day,realm,lots,activeId,wins,spent}`；每件 lot 保存 `{id,kind,item,count,status,price,leader,held,round,rivals}`，status 为 ready/bidding/decision/won/lost，对手只存白名单ID和ceiling。v11 的 `cleanAuction` 校验每日数量、境界、物品、步长/预算、状态/冻结款、所有权及累计记录。`validateAuctionLinks` 校验 activeId 与唯一合法 activity/pending、当前地点、开始时间/进度/轮次相符；正在举牌时还核对库存与药鼎资格。待选报价从图录重新构建，忽略原文及注入的 effects/AI 状态。冻结款损坏拒绝整档，而不是重置或尝试猜测退款；这是单机完整性校验，不是防作弊。

## 连续时钟与暂停

`minutes` 是从第 1 日零点起累计的游戏分钟，允许小数，是唯一模拟时间。顶部只显示整分，存档不舍弃小数。`GameClock` 按动画时间戳差计算：现实 1 秒 = 游戏 1 分钟；支持 1/3/10 倍，倍率同时影响全部模拟，而不是只加快人物动画。运行且无操作时，时间照常流逝。

暂停理由集合包含手动、面板、事件、菜单和存档冲突，不包含页面隐藏。只有全部理由解除才运行。关闭面板不能解除手动暂停；新游戏自动运行，载入旧游戏默认手动暂停。切换标签页/应用、`pagehide` 和长帧间隔都不会自动添加暂停理由；页面生命周期变化仍补存。

前台动画回调和仅在 `document.hidden` 时运行的每秒心跳共用一个时钟，均传入 `performance.now()`，按时间戳去重，旧回调不回退基准。隐藏页计时器被浏览器延迟时，同一会话的经过时间加入内存余量；每次回调最多推进四批、每批不超过 60 游戏分钟，余量留待下次，避免单次无界循环。`G.advance` 仍处理每个资源、订单、午夜和事件边界；事件、结局、破产或主动暂停立即清空剩余时间，不越过玩家选择。暂停、读档及倍率切换重置时钟基准，不把暂停期间折算成收益。

浏览器可能节流、冻结或销毁后台页面，不能承诺操作系统后台持续执行。仍存活的会话恢复执行时按上述规则推进；时钟余量不存入存档，关闭/重载页面和切换存档没有离线收益或离线房租。

`G.advance` 接收 0–1440 分钟的有限非负增量，采用最长 1 游戏分钟的小步积分，并进一步切分到午夜、06:00/18:00、未接订单消失、补单、车况阈值、资源耗尽和行动完成边界。遇到待选剧情立即停止，余下增量丢弃；读取/等待 AI 的时间不会回来补算。随机数只在定义的周期和完成节点抽取，不能按渲染帧数抽取。

`app.js` 只有一个动画循环；普通帧更新人物坐标、当前路线和待接订单的圆形消失进度环，状态栏约每 100 毫秒更新，重大状态变化通过 `revision` 触发完整刷新。顶部状态栏的结构只在首次进入局内时创建；后续完整刷新不替换 `.time-controls` / `#time-speed`，而由 `renderLive()` 原位更新姓名、境界、货币、天气、资源和时间等动态内容，避免原生选择框在世界刷新时被销毁。地图缩放、平移只改变视角。配送点新增时由 SVG 内层视觉组执行淡入弹出，移除时先标记为不可交互再缩小淡出；减少动态效果偏好下立即移除。日志只写开始、结束、停止、事件和生活结算，不逐帧记录。

110 个地点位于 11×10 正交路网，跨江只有四座桥（y=300/660/1020/1380）。世界边界为 2660×1860，每地图单位仍为 3.5 米。原 7×6 城区只向东、向南扩展，旧地点 ID、坐标和最短路线不改变。Dijkstra 计算道路最短路径。途中使用连续 `{x,y}` 和当前路线累计距离，而不是起终点切换或动画障眼法。离开地点后 `position=null`，不能继续使用原地点服务。路段内改道以当前坐标连接合法路段两端，不能吸附回起点或横穿江面。

`data.js` 中 `ROAD_NODES` 和 `ROAD_EDGES` 是地图绘制、寻路、途中位置校验共用的唯一道路拓扑，桥梁配置为 `ROAD_LAYOUT`。新增四个片区由 `DISTRICTS` 配置名称、坐标与描述，57 个地址均非永久显示；全城仍只有 9 个常驻服务/住宅标记，普通任务数量保持白天 6、夜间 4。不得因增加地点而重排任何已发布地点 ID。

寻路按起点缓存完整最短路树：精确节点最多缓存 110 份，连续道路位置仅缓存最近一份，防止每帧坐标令缓存无限增长；只缓存静态道路几何，不缓存天气、速度、消耗或随机结果。返回路线使用独立坐标对象，不暴露缓存。全城视图的缩放下限随视口计算，320/390px 也能容纳全部道路；缩放不改变地图距离。

预计耗时为 `km / speed × 60`，只在显示时向上取整。实际每一步按速度积分距离；电量、体力、耐久按实际路程扣除。骑行基础 22 km/h，速度每级 +4；车况到 20 及以下乘 0.7；步行受身法和轻身术影响，二者受天气影响。天气、车况或心法变化后，用新的速度计算余程。出发仍预检全程电量与体力；途中耗尽时停在当前坐标，不无电骑行。

## 持续行动与结算

行动保存 `kind/params/target/phase/duration/elapsed/startedAt/route/travelled/recovery/gainedQi`；阶段为 `travel` 或 `work`。需要路程的睡眠、拜访、搬家先真实移动，到达后才执行当地动作。零距离不产生虚构路程，仍通过同一完成路径处理。

| 行动 | 时长与结算 |
| --- | --- |
| 原地休息 | 60 分钟，体力 +38、气血 +8、灵力 +10 按进度恢复 |
| 睡眠 | 返回当前住处后 480 分钟，固定恢复或开始睡眠时的补满差额逐步生效 |
| 修炼 | 吐纳 45 / 入定 90 / 淬体 30 分钟，逐步消耗体力、增长修为；昼夜按实际时段计算，统计与随机事件仅完成后触发 |
| 原地充电 | 先付 ¥8，10 分钟按开始时电量缺口逐步补满，无地点要求；`G.CHARGE` 统一提供引擎、UI 和存档恢复数值 |
| 维修/治疗/用餐 | 当地开始时付费，按进度恢复；维修、治疗 30 分钟，用餐 20 分钟 |
| 升级 | 修车铺付费后 45 分钟，完成才提升等级 |
| 炼药 | 先在长乐集购买并切换药鼎；当前有 24 种药鼎、64 种药材、108 张丹方。开炉时按丹方一次性扣全部药材与灵力，持续 18–48 分钟，中断不退投入。丹方只定义配伍、火候与难度；丹药分一至九阶，成品阶数受当前药鼎阶位和炼药师阶位共同限制。药鼎、悟性与熟练度仍影响成丹率和额外产出；完成一炉后才增加熟练度 |
| 突破 | 开始投入本阶需求修为、20 体力及可选丹药；60 分钟完成判定。失败退回需求减去其 25% 向下取整值，中断不退投入，防止免费重试 |
| 探索/拜访 | 当地探索 30 分钟或到达后交谈 20 分钟，完成才生成事件和更新统计 |
| 气血耗尽救助 | 沿道路以救助速度转运至医馆，再治疗 180 分钟，无瞬移跳时，不可取消 |
| 耗时剧情选项 | 提交时支付负的金钱/外卖币/体力/灵力及物品成本，耗时结束应用其余结果；已提交选项不可取消 |
| 系统与物品 | 兑换/签到/领奖、允许条件下服药等即时事务为 0 分钟，不刷新整批订单 |

每跨入第 7、14、21… 日零点，先扣当前住处完整周租。不足则立即写入 `gameOver`，不再发放尚未完成行动的结果。若与交付或入住同刻，房租优先，不能预支配送收入；新住处仅在真正完成搬家时生效。日志使用游戏时间，`Date.now()` 仅用于存档更新时间等元数据。

`REALMS[].levels` 是各境界阶段数量的唯一配置；`G.realmLevelCount`、`realmLevel`、`realmLabel`、`realmNeed`、`nextRealmLabel` 与突破结算共用配置。凡人只有一阶段，从炼气到渡劫各九重；只有渡劫九重返回零需求与空下一境界。`player.realm` 保留原索引0–5并追加6–9，凡人 `realmLevel=1` 但不显示后缀。资源强度 `realmRank` 对炼气及以上仍为 `realm*9+level-1`，它是强度而非82阶段的序号，避免削减旧角色上限。UI、存档列表、角色卡和AI上下文统一使用境界标签，不写死化神封顶。

`player.mortalProgress` 只用于迁移旧凡人的成功投入，取 `LEGACY_MORTAL_PROGRESS` 白名单值；新档为0，普通跨入炼气时归零。旧凡人途中小重以 `activity.params.legacyMortalLevel` 校验原抵扣与本次投入，完成成功只增加抵扣，不创建分重状态；旧九重按新剩余门槛恢复为正常跨境。`legacyMajorBudget` 仅保留旧v5非凡人大境突破预算，限原六境的九重状态；两种衔接不能混用，保存到v13后仍重新校验。

### 炼药数据模型

炼药内容集中在 `data.js`：`ALCHEMY_MATERIALS` 固定为 64 种药材，按一至九阶分层；`ALCHEMY_RECIPES` 固定为 108 张丹方，每张保存 `product/materials/mana/duration/base/need/realm/minCauldronTier`；`CAULDRONS` 除“无药鼎”外固定为 24 种器型，并带有 `tier/success/extra/quality/realm`。丹方 ID 与丹药物品 ID 分离，旧 `heal/stamina/qi/foundation` 丹方 ID 保留用于途中存档兼容。

丹药本身由 `PILL_TYPES` 定义 12 类基础产物，每类生成一至九阶成品物品。一级成品沿用旧 ID（例如 `heal`、`foundation`），二至九阶使用带阶位的派生 ID，因此旧事件与旧库存可以继续工作。炼成时先按丹方判定是否成丹；若成功，再由 `G.alchemyPillTier` 根据当前药鼎阶位与炼药师阶位给出成品阶数，并写入对应阶位库存。高阶破境丹在突破时按玩家选择自动消耗现有最高阶，阶位越高加成越大。

`alchemy.cauldron` 保存当前使用的药鼎索引，`alchemy.cauldrons` 保存已拥有的 24 鼎索引集合，`alchemy.formulas` 保存已获得丹方 ID。购买和切换药鼎都只能在长乐集执行；同阶药鼎可以有不同成丹率、额外产出和成色修正。

丹方分为“获得”和“参悟/可炼制”两层。新存档 `formulas=[]`；未获得丹方不在 UI 中显示名称、产物、配伍或条件，隐藏 ID 开炉错误也不回显丹方名称。已获得丹方仍需满足熟练度、境界、最低药鼎阶位、全部药材与灵力条件才能开炉；无效开炉不得部分扣料。

`ALCHEMY_RECIPES[].acquisition` 保存互斥来源：`shop` / `story` / `bond`，各 36 张。每个丹药类型的九种配伍按三组分配，每个渠道三张。`FORMULA_STORY_SOURCES` 配置首个委托及五个主线节点（每批六张），`FORMULA_NPC_PRODUCTS` 配置六位 NPC 分别擅长的两类药，`FORMULA_BOND_MILESTONES` 配置章数 1/2/4 与信任 3/9/20（每批两张）。获取条件不由炼制难度推导，先进丹方也能先收录再等待参悟。

`G.formulaMarketCandidates` 只返回当前境界允许的未拥有 `shop` 丹方；长乐集“未知残卷”使用原世界 RNG 随机且无重复，不接受指定隐藏 ID。买空、钱不够或地点错误保持原状态不变。普通探索只保留药材和事件流程，不再从全丹方池直接掉落。

`G.syncFormulaRewards` 只作用于引擎已复制的状态与读档迁移副本，在成功事务末尾、世界行动完成节点和剧情 flags 恢复后的读档清洗中调用。不在每帧或渲染中分发，不额外抽随机数、不扣钱也不推进时间。已拥有集合是幂等判断依据，已有丹方不撤销，游戏结束后不再发奖。

现有主线 flag 表示“已注入”，不是“已结算”。因此剧情奖励要求 flag 为真且当前 `pending.templateId` 和进行中的 `choice` 事件都不是该主线；首个委托要求 `claimed` 包含 q1。待选、耗时选择及其途中读档都不能提前获得奖励，同刻房租破产先中止结算。羁绊要求已经结识、实际完成章数与信任同时达标，路线选择不做门槛。`G.formulaBondProgress` 按章数排序未得奖励，支持旧档仅拥有部分丹方的情况。

1.4.2 曾保持 v9 丹方所有权集合；1.5.0 在保留该集合的基础上增加 v10 功能所有权。`progression.js` 先恢复完整剧情 flags，再一次性补领已完成主线/羁绊应得而未拥有的丹方；不会把旧档已购得的专属方收回。`G.formulaSourceLabel` 是当前配置的获取途径，不宣称它记录了旧档中的实际来源。羁绊页仅对已遇见 NPC 显示数量与下一条件，丹方页仅对已得到的丹方显示途径。

`seed` 随存档保存，采用 xorshift。相同种子、相同游戏时刻的指令和等量游戏时间应得到相同结果，允许浮点积分误差；创建时间与随机 ID 不属于世界随机源。

## 配送与事件

订单在地图上展示预计行程、资源需求和“多久后从地图消失”。内部为兼容旧存档仍使用 `expiresAt`，但该字段只表示未接订单的地图消失时刻。确认接单时校验 ID 尚未消失、全程资源与特殊要求，不再比较预计抵达时间；通过后将票据移入独立的 `activeOrder`，启动移动，不发奖励。已接任务点持续显示，不受原消失时间和待接订单刷新影响。到达后创建包含 `delivery` 票据的 `pending`，或直接结算无事件订单。票据从活动订单转入待选事件时只保留一份。

待接订单到达消失时间即移除，每 15 游戏分钟和有意义的世界行动完成后只补空缺，不重抽仍有效的订单。地图以圆形进度环显示剩余停留比例；圆环使用 SVG 局部坐标原点 `(0,0)` 作为中心并通过 `rotate(-90 0 0)` 从正上方开始绘制，避免 CSS 变换盒导致与配送点错位。出现和消失动画只属于 DOM 表现，不改变规则时间。暂停和即时事务不制造免费刷单。普通随机事件仍由配送、探索、修炼等行动完成触发，不新增每帧抽奖。

`choose` 要求传入正确事件ID和合法选项索引。选择不足以支付的成本会失败、状态不变；正确选择立即扣除规定成本；有时长的选项转换为不可取消的持续行动，完成后应用剩余效果、推进人物章节并结算票据。零时长选项立即完成。配送事件耗时不会形成超时处罚；只要订单在消失前已经接下，最终按票据原现金和正常口碑规则结算；外卖币以实际结算前系统是否已开启为门槛，开启后按票据原额发放。

处理事件期间禁止其他世界行动。重复旧事件ID、旧订单ID或多次点击不能重发奖励。每个关键人物章节都至少有一个零金钱/灵力/道具成本的选项，避免把玩家困在强制对话里。

人物采用发现制。`bonds[npc].met` 默认是 `false`：配送票据带有人物ID时（不要求是其常约地点），订单结算会将其设为已结识；经典随机事件可用 `encounterNpc` 在事件触发时解锁角色。应用层只渲染已结识人物，`visit` 在规则层也会拒绝未结识角色，不能靠直接构造按钮绕过。旧存档迁移时，已有好感、信任、章节进度或关系路线会推断为已结识。

关键成长主线由 `progression.js` 管理。它保留解锁外卖系统至人间即阵心的前七阶段，并追加化神至渡劫五章，共十二个阶段，并在满足配送数、境界、已结识人物数后注入固定 `pending` 事件。关键事件使用 `kind: story`、`source: classic`、`aiStatus: skip`，不会进入普通随机事件池，也不会被 AI 替换。对应 `flags.story*` 会随存档恢复，避免重复触发。

商城开放同样由 `progression.js` 约束：基础补给要求系统已开放且为凡人阶段，高阶材料与心法要求炼气，高阶法器要求筑基。规则层会拒绝未解锁兑换，UI 不展示尚未开放的商品。

## 存档结构

主要字段：

```js
{
  schemaVersion: 14,
  id, name, mode, createdAt, updatedAt, seed,
  turn, revision, minutes, position, location, residenceId, gameOver, transport, weather,
  activity, activeOrder, orderRefreshAt,
  player: { money, coins, health, stamina, mana, qi, realm, realmLevel, mortalProgress,
            insight, constitution, agility, luck, karma, rep },
  vehicle: { battery, durability, levels: { speed, battery, durability } },
  alchemy: { cauldron, cauldrons, formulas, xp, brews, successes },
  auction: { day, realm, lots, activeId, wins, spent },
  inventory, learned, equipment, stats,
  bonds: { /* 每人 met, affinity, trust, stage, path, lastTalkDay */ },
  daily, claimed, unlockedFeatures, unlockedPlaces, unlockedEndings, ending,
  flags, recentEvents, pending, eventResult, orders, logs, lastRoute

```

存储键：`night-courier:saves:v14`；仅在新键不存在时从 v13、v12、v11、v10、v9、v8、v7、v6、v5、v4、v3 旧键显式迁移（新键的空列表不是缺失，不复活已删除存档）；上一写入备份键：`night-courier:saves:backup`。列表最多12份；每份日志最多180条，防止无界增长。

`sanitizeSave()` 不把任意原始对象合并进状态，按字段白名单重建，规范数值范围，并校验人物进度、住处、破产结束状态、事件模板及待结算票据。v1–v6 只有识别到的重建字段迁移，不对未知原游戏做猜测。进行中行动按类型白名单恢复；重建合法路线，并校验当前坐标与路程一致、当地服务位置和待结算票据互斥。时间、资源、路程保留小数，不重复收取已支付成本。

应用 1.6.0 将存档提升到 v11，新增上述拍卖状态。v10及以前初始化空拍卖记录，保留资产与原活动；v11缺失拍卖数据视为损坏。先恢复拍卖图录，再恢复其 pending/activity 并交叉验证，不重复冻结、退还或发物。全部旧格式迁移继续保留，图录按档独立，无离线补算。

应用 1.5.0 将存档提升到 v10，新增 `unlockedFeatures`。`restoreFeatureUnlocks` 在状态与合法在途行动恢复后处理：v10 按白名单去重，并补足已有功能的前置；v9 及更早没有该字段时，根据已经完成的里程碑以及系统收益、修为/境界、探索记录、丹方/药鼎/材料/炼药经验、车辆升级和结局记录推断已经使用的功能。合法在途付费行动对应的入口继续开放，不重收成本。不把空白 v9 档全开；只补与已有能力相关的入口，保留主线待选/进行中语义。progression 恢复剧情 flags、补领旧奖励后再静默同步一次，重复读取不重复写解锁日志。多存档各自保存，无全局功能所有权。

应用 1.4.1 将存档提升到 v9，新增 `alchemy.formulas`。v8 及更早存档没有显式丹方所有权：迁移时把当时按当前境界和炼药熟练度已经可使用的丹方记为已获得；若存在进行中的炼药，即使该丹方不在计算结果中也强制加入，以保证当前炉可以恢复。v7 的旧三档药鼎继续通过 `LEGACY_CAULDRON_MAP` 映射到新 24 鼎中的对应器型；旧 `heal/stamina/qi/foundation` 库存仍作为一阶丹保留。旧 v1–v6 若没有 `realmLevel`，仍默认从原大境界一重继续；旧 v5 正在炼药但没有炼药字段时仍补一口基础药鼎。1.2.0 的充电兼容继续保留：旧版进行中充电若 `duration===30`，按 `elapsed / 30` 的完成比例换算至 10 分钟，保留游戏时钟、现有电量、恢复快照和已付费用，不立即发放收益。旧城区路线兼容校验继续覆盖扩城前存档。

运行约每 10 现实秒自动保存，行动开始/完成、选择、暂停、面板打开、返回菜单和页面隐藏等关键节点补存。读取后以暂停状态恢复，不补算离线时间。

导入解析最大2MB，整个批次先验证再写入；重新生成ID避免覆盖。主记录损坏时尝试读取上一写入备份，保留原损坏文本并提示，而非静默用空数组覆盖。写失败则设置dirty，后续返回菜单仍保留内存进度，直到导出或成功写入。

localStorage 的单项写入不等同数据库事务。多标签页用 `storage` 事件提示冲突并暂停陈旧页面的行动，不能视作多人并发锁或服务端安全保障。

## AI 代理与信任边界

服务端 `createApp(options)` 使用 Node 内置 HTTP；静态文件只服务明确列出的 public 文件，不能读取 .env 或源码。默认127.0.0.1，检查 Host 与来源，限制 JSON 请求大小16KB、上游响应128KB、每分钟12次、并发2次、上游超时15秒。

前端等待最长18秒，绑定存档ID、事件ID和请求序号；切存档、返回首页、做出选择会取消在途请求，迟到结果直接丢弃。没有配置/返回异常时保留经典事件并记录回退，不把存档模式改为 classic。

请求送出系统是否已开放的布尔值、角色名、境界名称、时间、天气、地点、部分属性、事件素材和最近三条日志。姓名及日志视作不可信创作素材，不是系统指令。

返回值只接受三选项JSON，字段与取值白名单如下：

| 字段 | 允许整数范围 |
| --- | --- |
| money | -15 … 20 |
| coins | 0 … 2 |
| health/stamina/mana | -10 … 8 |
| qi | 0 … 20 |
| karma/rep | -2 … 3 / -2 … 2 |
| affinity/trust | 0 … 6 / 0 … 3，仅人物日常交谈 |

每选项最多4个效果，至少一个完全非负选项；文本长度有上限。可见文本会转义，不能注入HTML执行。不存在 eval / Function 执行 AI 文本，也不接受位置、境界、模式、道具所有权等任意写入。

这些限制约束模型输出与误操作，不阻止玩家改自己的本地存档。当前服务器没有用户认证，不能直接当公共商业AI代理使用。

## 扩展方式

新增事件：在 `data.js` 定义唯一ID、kind、title、text、三项 choices；至少一个无支付障碍选项。新增特殊资源效果要同时改 `effectBlock`、`effects`、存档白名单和测试，不能只改界面。

新增地点：地图与寻路共用网格，当前每地点必须位于合法节点。若扩大网格，`route()` 中边界与桥梁约束也要一起改，不能只画新建筑。

新增物品：修改 `ITEMS` 与引擎处理，同时核对去重购买、装备上限、存档清洗及导入迁移。新增境界会影响资源上限与突破要求，应加端到端可达性测试。

修改格式：提升 schemaVersion，保持显式迁移。先用典型待选配送事件、已升级车、AI模式和人物分支存档做往返测试。

修改源码后执行 `npm run check && npm test && npm run build`；界面修改另执行 `python tests/browser-smoke.py`。不要只手改 dist；否则下次构建会覆盖修改。
