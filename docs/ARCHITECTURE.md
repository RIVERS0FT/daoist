# 技术架构与扩展边界

本文档只描述**当前技术架构、状态推进方式和工程约束**。当前玩法规则见 [GAME_DESIGN.md](GAME_DESIGN.md)，版本历史见 [VERSIONS.md](VERSIONS.md)。

当前应用版本：**1.18.0**  
当前存档 schema：**v21**  
当前存储键：`night-courier:saves:v21`

- `README.md`：项目入口、运行、文档导航、验证与发布摘要。

## 2. 运行时模块

浏览器端使用原生 JavaScript IIFE，各模块注册到 `globalThis.NightCourier`。

加载顺序：

```text
data → npc-profiles → engine → clock → storage → progression → map → app
```

主要职责：

| 模块 | 职责 |
| --- | --- |
| `data.js` | 世界、地点、道路、物品、NPC、事件、数值配置 |
| `npc-profiles.js` | 人物性格、职业边界、画像/AI提示词 |
| `engine.js` | 核心行动校验、状态复制、结算、路线与规则查询 |
| `clock.js` | 连续时间、倍率、暂停理由与前后台时钟 |
| `storage.js` | v21 存档、迁移、清洗、导入导出与备份 |
| `progression.js` | 功能开放、固定主线、章节侧写与成长扩展 |
| `map.js` | SVG 地图、路线表现、订单点与手势 |
| `app.js` | UI 渲染、面板、事件请求与输入编排 |
| `server.mjs` | 本机静态服务与受限 AI 代理 |

服务端可以复用可信静态数据，但不能把浏览器本地状态当作服务端权威账户数据。

## 3. 状态推进模型

核心原则：**界面不能直接写游戏结算状态**。

```text
玩家输入
  ↓
G.perform(oldState, action, payload)
  ├─ 校验失败 → 返回原状态，不部分扣费
  └─ 即时事务 / 创建 activity
                      ↓
                 G.advance(state, dt)
                      ↓
       时间、路线、消耗、午夜、完成节点
                      ↓
      事件 / 结果 / 解锁提示 / 主线 / 保存
```

### `G.perform`

负责：

- 验证功能是否已开放。
- 验证地点与资源是否满足。
- 验证行动是否与现有 activity / pending 冲突。
- 执行零耗时事务。
- 创建一个持续行动。

无效指令必须原子失败：不能先扣钱、再发现条件不满足。

### `G.advance`

是世界时间的唯一持续推进入口。

它负责：

- 连续移动坐标。
- 按实际时间/距离扣除或恢复资源。
- 订单消失与订单补充边界。
- 昼夜与房租边界。
- 行动完成。
- 剧情注入与待选节点。
- 终局优先级。

不能通过 UI 定时器单独发奖励，也不能通过动画结束事件代替规则结算。

## 4. Activity 与单行动约束

同时只能有一个主要 `activity`。

持续行动可包含：

- `kind`
- `params`
- `target`
- `phase`
- `duration / elapsed`
- 路线与累计移动距离
- 已投入成本或渐进收益快照

常见阶段：

- `travel`：沿路移动。
- `work`：到达后执行当地行为。

“停止”与“暂停”必须分离：

- 停止：结束可中断的 activity，保留真实已发生进度，世界继续。
- 暂停：冻结世界时间。
- 已提交的耗时剧情选择与拍卖轮次不能当成普通行动免费取消。

## 5. 连续时钟与暂停

`minutes` 是唯一游戏时间，允许小数。

时钟由 `GameClock` 管理，所有暂停理由组成集合：

- manual
- panel
- event
- menu
- conflict

页面隐藏不是暂停理由。

前台 requestAnimationFrame 与后台心跳共享同一时钟基准，使用经过的墙钟时间计算游戏分钟。长时间回调按批次推进，遇到剧情、终局或暂停立即停止。

关键限制：

- 不存储“离线时间余量”。
- 关闭或重载不补算。
- 读取存档默认手动暂停。
- 倍率改变只改变模拟速度，不跳过内部结算边界。
- 随机抽取只能发生在已定义的世界节点，不能按渲染帧抽。

## 6. 道路、移动与地图

`ROAD_NODES` / `ROAD_EDGES` 是以下模块共用的唯一道路拓扑：

- 路线计算。
- SVG 道路绘制。
- 途中位置校验。
- 存档恢复。
- 改道。

最短路径使用道路图而不是直线距离。途中位置为连续坐标；离开地点后不能继续使用原地点服务。

扩图要求：

- 不重排已有地点 ID。
- 不移动旧坐标。
- 新地点必须接入合法路网。
- 地图和规则必须使用同一份道路配置。
- 普通订单标记的动画不能影响世界坐标或命中区域。

## 7. 配送票据与地点所有权

待接订单与已接订单分开保存。

票据在创建后固定：

- 目标地点。
- 现金与外卖币基础奖励。
- 特殊条件。
- 可选 NPC 关联。

接单后票据转入 `activeOrder`，不能因刷新、暂停或读档重抽。

地点所有权由 `unlockedPlaces` 保存。成功配送结算时才调用地点解锁逻辑；到达、待选、中断、取消或未完成耗时选项都不能授予地点。

规则层必须校验地点所有权，不能仅靠隐藏 UI 防止异地操作。

## 8. 事件、选择与结果回执

普通剧情流程：

```text
pending
  ↓ choose
即时结算 或 耗时 choice activity
  ↓
eventResult
  ↓ ackResult
后续地点/人物/功能回执
  ↓
下一段 pending / 地图
```

`eventResult` 是一次性已结算回执，不是可重复执行的奖励票据。

规则：

- 选择必须匹配正确 event ID 和合法索引。
- 成本不足时整次提交失败。
- 耗时选项先提交必要投入，完成后才应用剩余结果。
- 配送结算只发生一次。
- `ackResult` 只确认阅读，不再次发奖、不推进时间、不抽随机。
- 未读结果冻结世界推进。
- 后续主线可以排队，但不能覆盖当前结果。

固定主线、人物关键章节和拍卖决策使用可信模板恢复，不能从存档的任意文本或 AI 输出恢复效果。

## 9. 解锁与进度

功能定义集中在 `FEATURE_UNLOCKS`，面板映射集中在 `FEATURE_PANELS`。

同一条件必须同时用于：

- 规则层 action 校验。
- 导航显示。
- 顶部入口。
- 地点快捷操作。
- 解锁提示。

`G.featureUnlocked` 等查询必须是纯查询，不能因打开面板或渲染 UI 写入所有权。

人物发现、地点发现、玩法解锁是三种独立所有权，不能互相推导。

当前玩法门槛写在 GAME_DESIGN，不在架构文档重复维护。

## 10. 主线与角色资料

关键主线由 `progression.js` 注入，固定事件使用 classic source，并跳过 AI 替换。

章节人物侧写 `G.CHAPTER_CHARACTER_BEATS` 是静态只读配置：

- 只读取已结识人物。
- 不推进人物 stage。
- 不发奖。
- 不写存档。
- 不发送未来人物剧情给 AI。

NPC 身份、年龄、职业以 `data.js` 为主；扩展人设在 `npc-profiles.js`。导出脚本从同一源码生成 `NPC_PROMPTS.md` 与 JSON，禁止只改导出文件。

周野的分阶段身份披露必须按已结算阶段裁剪，不能把完整制作端剧透直接发送给早期 AI。

## 11. 存档 v21

当前：

```text
G.VERSION = 21
G.STORAGE_KEY = night-courier:saves:v21
G.MAX_SAVES = 12
```

状态类别包括：

- 基本元数据：id、name、mode、seed、revision、时间。
- 玩家属性与资源。
- 电动车。
- 炼药与药鼎/丹方所有权。
- 拍卖状态。
- 宗门状态。
- NPC bonds。
- 功能、地点、结局所有权。
- 订单与 activeOrder。
- activity。
- pending / eventResult。
- 地点、人物和功能解锁回执。
- 主线 flags。
- 日常统计、日志与最近事件。

`sanitizeSave` 必须按白名单重建，而不是把原始 JSON 深合并进新状态。

迁移原则：

- 只迁移已知旧结构。
- 新键存在但为空，不复活旧键。
- 在途行动必须恢复真实剩余进度与已支付成本。
- 不重复发奖、不重复扣费。
- 损坏关键关系或事务链时拒绝读档，而不是猜测修复。
- 历史已结算文本保留原文。
- schema 变化必须新增往返、途中与非法数据测试。

本地完整性校验不是服务端防作弊。

## 12. AI 代理与信任边界

`server.mjs` 使用 Node 内置 HTTP，默认只监听本机。

AI 请求：

- 只发送完成创作所需的有限上下文。
- 用户姓名、日志和模型输出都视作不可信文本。
- NPC 日常按 NPC ID 从服务端可信目录重建人设。
- 不接受客户端自写系统提示词覆盖角色身份。

AI 响应：

- 只接受规定 JSON 结构。
- 只允许白名单效果和数值范围。
- 不能设置地点、境界、模式、功能所有权或任意物品。
- 不执行 HTML/JS。
- 超时、格式错误或效果越界时回退经典内容。
- 迟到响应不能覆盖已经选择或结算的事件。

密钥：

- 只从服务端环境读取。
- 不写入前端、存档、日志、构建产物或仓库。

当前代理无用户认证，不应直接作为公共商业 AI 后端。

## 13. UI 与渲染边界

`app.js` 负责把状态投影为界面，不应成为业务规则第二来源。

要求：

- 普通帧尽量局部更新，不重建完整地图。
- 顶部时间倍率选择框保持 DOM 稳定。
- 地图缩放/平移只改变视图。
- 动画不改变规则状态。
- 所有用户可见文本做必要转义。
- 长导航在移动端内部滚动。
- 系统减少动态效果时移除非必要动画。
- 行旅日志是唯一长期行为日志区。

## 14. 测试

每次源码修改至少执行：

```sh
npm run check
npm test
npm run build
```

涉及界面/浏览器行为还必须执行：

```sh
python tests/browser-smoke.py
```

新规则需要同时增加：

- 正常路径。
- 条件边界。
- 失败原子性。
- 中途存读。
- 重复提交。
- 房租/终局同刻优先级（相关时）。
- AI 不可越权（相关时）。
- 桌面与窄屏交互（相关时）。

测试报告写验证事实，不反向定义玩法。

## 15. 构建与发布

### 单文件构建

`scripts/build.mjs` 将可信 `public/` 源码生成 `dist/index.html`。

`dist` 是产物，不是修改源。

### CI

`.github/workflows/ci.yml` 用于 PR/代码验证。

### RIVERSOFT

`.github/workflows/deploy-riversoft.yml` 是当前唯一静态线上发布流程。

`main` 推送后：

1. Node 22 源码检查。
2. 完整 Node 测试。
3. 单文件构建。
4. Chromium 回归。
5. RIVERSOFT bundle 检查。
6. 保存验证过的 `dist` 工作流产物。
7. 独立 publish job 获取 `production` 环境中的 `RIVERSOFT_TOKEN`。
8. 发布 `daoist` slug。
9. 下载公网 `index.html` 并与构建文件做 SHA-256 比对。

GitHub Pages 已删除，不应重新添加 Pages workflow，除非用户之后明确改变发布策略。

RIVERSOFT 静态沙箱不等于完整 Node 环境：真实 AI 代理和可靠本机浏览器持久化仍以 `npm start` 为完整运行方式。

## 16. 扩展检查表

新增或修改玩法时：

1. 先修改 GAME_DESIGN 的当前规则。
2. 修改 `data.js` 配置与/或规则模块。
3. 核对 `G.perform` 的规则层入口。
4. 核对 `G.advance` 的真实耗时结算。
5. 核对存档白名单与迁移。
6. 核对 UI 是否只展示规则查询结果。
7. 增加边界测试。
8. 如果形成新应用版本，在 VERSIONS 按“新增 / 修复 / 优化”三段记录。
9. 更新对应 TEST_REPORT。
10. PR CI 通过后 squash merge。
11. 合并到 main 后验证 RIVERSOFT verify、publish 与公网哈希。
